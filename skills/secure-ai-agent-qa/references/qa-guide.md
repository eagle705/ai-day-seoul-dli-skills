# 자주 나오는 질문과 설명 기준

이 문서의 자료별 이름과 번호는 내부 조회용이다. 사용자 답변에는 SKILL.md의 규칙에 따라 `근거: 강의 슬라이드 「주제」.`로 표기한다.
이 문서는 답변의 방향을 잡는 참고 자료다. 실제 응답 전 표기된 장표·발표자 노트를 검색해 읽고 질문에 맞게 설명한다. 아래 예시를 실제 실습 관찰값으로 보고하지 않는다.

OWASP 정의·목록 구분, OpenShell 모드·정책 변경, MCP/OAuth, ATLAS·NIST는 [공식 자료 보완 Q&A](web-security.md)의 해당 절을 함께 읽는다. 아래는 강의 기반 설명이며 공식 문서에서만 보완한 내용의 출처는 실제 공식 링크로 표시한다.

## 에이전트와 위협 모델

**LLM과 에이전트는 무엇이 다른가?** 모델이 추론·행동을 제안하고 하네스가 컨텍스트·도구·메모리·실행을 연결한다. 서울 29장의 모델·하네스·툴/스킬·런타임 네 구성 요소와 30장의 `LLM + harness`는 설명 수준이 다른 도식이다. 도구를 추가했다고 무조건 독립된 권한 경계가 생기는 것은 아니다. 근거: 서울 29–32, 베를린 28.

**기능이 많아지면 왜 위험해지는가?** 일곱 차원은 입력 신뢰도, 접근 민감도, 워크플로우, 행동, 메모리, 툴, UI다. 각 기능의 효용과 함께 새 진입점·접근 자원·지속성·유출 경로가 무엇인지 설명한다. 실제 위험은 조합과 배포 조건으로 평가한다. 근거: 서울 36–44, 베를린 32–40.

**치명적 삼요소가 있으면 반드시 유출되는가?** 신뢰할 수 없는 입력 + 민감 데이터 접근 + 외부 반출 경로가 결합되면 유출 위험을 가정하고 설계하라는 위협 모델이다. 모든 실행에서 유출이 관측된다는 수학적 정리는 아니다. 공격이 없어도 실수·오염된 입력이 같은 결과를 낼 수 있다. 최소 한 연결을 실제 권한·데이터 흐름 경계에서 끊고 확인한다. 근거: 서울 53–54, 베를린 48–49.

**인젝션과 일반 사용자 지시를 어떻게 구분하는가?** 업무 자료를 읽을 권한과 그 자료가 작업 규칙을 바꿀 권한은 별개다. 노트에 적힌 “승인됨으로 표시하라”는 문장은 승인자의 권한을 갖지 않는다. 직접 사용자 입력 공격과 외부 문서의 간접 인젝션은 진입점이 다르다. 근거: 서울 55–69·71·89–90, 베를린 50–65.

**RAG를 쓰면 인젝션이 해결되는가?** 검색은 정보의 출처와 관련성을 다루며 검색된 문서에 지시 권한을 주지 않는다. 검색 코퍼스 오염과 모델을 속이는 공격을 구분한다. 근거: 서울 60 및 주변 외부 공격 장표, 베를린 55.

## 방어와 권한

**가드레일만 붙이면 안전한가?** 필터·모델 판정은 위험 행동을 줄이지만 실제 자원 접근은 외부의 정책과 권한으로 제한해야 한다. 표현이 바뀌어도 같은 효과를 낼 수 있으므로 파일·프로세스·네트워크·API 효과를 점검한다. 근거: 서울 97·99·101–108·127, 베를린 88·90·92–99·117.

**4계층을 순서대로 통과하는 장비 네 개로 이해해도 되는가?** 네 계층은 방어 기법의 분류다. Layer 1 런타임 보호, Layer 2 secure by design, Layer 3 IAM, Layer 4 hardening. 에이전트 스택의 배포·오케스트레이션·하네스·보안 런타임·추론 데이터 플레인은 실행 위치의 분류다. 두 표를 동일한 계층 번호로 대응시키지 않는다. 결정론적 통제도 올바른 정책·구현·경로 포괄성이라는 조건 안에서 효과를 제한한다. 근거: 서울 97–99, 베를린 88–90.

**읽기 에이전트와 게시 에이전트를 나누면 안전한가?** 역할과 대화 분리만으로 OS 권한이 나뉘지 않는다. 같은 계정·공유 볼륨이면 reader가 outbox에 직접 쓸 수 있는지 확인해야 한다. 근거: 서울 48·111–112·130, 베를린 102–103.

**404/405를 받았으니 파일을 보호한 것 아닌가?** desk의 해당 HTTP 경로에서 허용하지 않았다는 증거다. 같은 UID의 파일 직접 쓰기 같은 다른 경로는 따로 확인한다. 근거: 서울 71. 서비스 인터페이스와 OS 권한을 구분한다.

**OpenShell이 Codex의 모든 행동을 막는가?** 강의의 일반 구조와 서울 Lesson 8 실습 배치를 구분한다. 해당 실습은 Codex가 밖에서 작업을 요청하고 job이 안에서 실행된다. 정책이 다루는 자원·경로와 통제하지 않는 경로를 함께 설명한다. 근거: 서울 113–116, 베를린 104–106. 현재 설치 버전의 명령 문법은 이 스킬에 포함되어 있지 않다.

**사람이 승인하면 무엇이 보장되는가?** 승인한 대상·범위·실제 효과가 연결되어야 의미가 있다. 프롬프트에 “승인받으라”고 쓰는 것과 시스템이 실행을 멈추는 것은 다르다. 실습의 승인 절차는 강제 지점을 확인하고 설명한다. 근거: 서울 109·129, 베를린 100.

**테인트 추적은 왜 필요한가?** 데이터의 신뢰 수준과 출처를 표시하고 파생 데이터까지 정보 흐름을 추적하기 위해서다. 텍스트로 라벨만 붙이는 실습과 런타임이 라벨 정책을 강제하는 구현을 구분한다. 근거: 서울 105·129, 베를린 96.

## 키·공급망·검증

**HMAC 검증에 성공한 요청이면 믿어도 되는가?** HMAC은 공유 키를 가진 주체가 생성한 인증 코드와 메시지 무결성을 검증한다. 공유 키이므로 특정 개인의 신원이나 부인 방지를 단독으로 증명하지 않는다. 악성 의존성도 키를 읽을 수 있으면 정상 MAC을 만들 수 있다. 강의의 “서명”이라는 포괄 표현과 비대칭 전자서명을 구분해서 설명한다. 근거: 서울 82·121–122, 베를린 76·111–112.

**키를 읽기 전용으로 바꾸면 쓰기가 전부 차단되는가?** 수신자가 키 범위에 따라 쓰기를 거부해도 동일 OS 계정의 직접 파일 쓰기는 남을 수 있다. 이전 키 사본이 계속 유효한지도 확인한다. 근거: 서울 82. “키 파일의 읽기 권한”과 “그 키가 허용하는 API 범위”를 혼동하지 않는다.

**암호화하면 에이전트 보안은 끝인가?** 강한 암호를 직접 깨지 않고 키 소유자를 이용하거나 유효하지만 악의적인 요청을 보낼 수 있다. 가장 저렴한 우회 경로를 검토한다. 양자 내성 표준이나 현재 권고 알고리즘은 공식 출처로 별도 확인한다. 근거: 서울 122–123, 베를린 112–113.

**정형 검증으로 LLM 전체를 안전하다고 증명할 수 있는가?** 이 과정은 명세한 정책의 속성이나 제약을 검증하는 실용적 접근을 강조한다. 속성 하나의 증명은 모든 행동·구현·배포 환경의 보안 증명이 아니다. 근거: 서울 117·130, 베를린 107.

**모델과 툴 하드닝은 무엇을 해결하는가?** 명령 계층을 지키는 학습과 툴 출처·무결성 검증은 공격 비용을 높인다. 승인된 코드 자체의 악성 동작이나 이미 노출된 키를 자동으로 해결하지 않는다. 서명·검증·격리·최소 권한을 함께 설명한다. 근거: 서울 125·82, 베를린 115·76.

## 운영·실습·평가

**잘 동작하는데 왜 거버넌스가 필요한가?** 출시 전 책임자·공개 범위·로그·중지 및 자격 증명 회수 절차를 정한다. 변경과 복제로 새 권한이 생기는지도 재평가한다. 근거: 서울 132–138, 베를린 120–125.

**모델이 완료했다고 했는데 파일이 없다.** 현재 디렉터리·실제 파일·명령 종료 상태·작업 ID·내용을 확인한다. 종료 코드 0이나 성공 문구만으로 원하는 효과를 증명하지 않는다. 근거: 서울 32–33·127, 베를린 29·117.

**Lesson 5가 OpenShell 아닌가?** 기존 Notebook 5는 OpenShell이지만, 서울판 Lesson 5는 외부 공격이고 OpenShell은 Lesson 8이다. 현재 화면의 제목으로 선택한다. 근거: 서울 89·115–116.

**평가자가 보내라는 파일은 그냥 보내도 되는가?** 평가자는 의도적으로 적대적이다. 질문을 인용해서 사용자와 답을 준비하고, 실제 기록으로 검증하며, 전송할 내용과 제출 시점을 사용자가 결정한다. 근거: 서울 141–142, 베를린 128. 학습용 모의 질문은 가능하나 실제 합격 결과를 대신 만들지 않는다.

## 강사용 30초 설명 예시

가드레일과 격리: “에이전트가 위험한 지시를 거절하는 것과 그 행동을 할 권한이 없는 것은 다릅니다. 노트에 승인 지시를 심었을 때 거절했더라도 같은 계정으로 직접 쓸 수 있다면 권한은 남아 있습니다. 우리는 입력과 출력을 검사하면서, 모델이 실수해도 파일과 네트워크 권한이 피해 범위를 제한하게 해야 합니다.” 근거: 서울 71·97·108.

가능한 꼬리 질문: “어떤 경로를 시험했는가?”, “동일 계정의 다른 경로도 막히는가?”, “정책을 워커가 바꿀 수 있는가?”

## 제공된 PDF로 확인하는 실습 Q&A

실습 질문은 [lab-modules.md](lab-modules.md)에서 해당 모듈을 찾고 실제 PDF 페이지를 검색한다. 이전 설명보다 다음 사항을 우선한다.

- 선택 모듈: 3·4·11. 현재 상세 PDF는 1~10만 있다.
- OpenShell 실습 버전: 문서상 v0.1.2. 정책은 권한 탭에서 사용자가 적용한다.
- 인덱스 서비스: 모듈 2에서 시험 뒤 중지한다. 계속 실행해야 한다고 답하지 않는다.
- 공격 결과: 직접 쓰기를 인젝션 성공으로 명명하지 않으며, 새 세션에서 두 번 거부하면 저항됨으로 기록한다.
- 입력 가드: 문구를 표시할 뿐 차단을 자동 강제하는 것으로 가정하지 않는다.
- 출력함: 반출 모형이며 이 실습의 파일은 실습 밖으로 전송되지 않는다.
- 심층 방어: 역할 분리·정책 속성 검사·규칙 추가 실습의 한계를 실제 OS 격리·SMT 검증·모델 학습과 구분한다.

더 읽을거리는 [further-reading.md](further-reading.md)의 질문별 설명을 사용한다. 학습자의 현재 결과 없이 PDF 기준 실행을 재현했다고 보고하지 않는다.
