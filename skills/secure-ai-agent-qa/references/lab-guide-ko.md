## 이 실습에서 반복하는 작업 방식

각 노트북은 대체로 다음 흐름으로 진행된다.

1. **목표 확인** — 현재 단계가 무엇을 만들거나 시험하는지 읽는다.
2. **지시 전달** — 화면의 지시문을 Codex 코딩 어시스턴트에게 보낸다.
3. **권한 검토** — 파일 쓰기, 명령 실행, 네트워크 요청 등의 승인이 나오면 대상과 범위를 확인한다.
4. **실행 관찰** — Codex가 어떤 파일을 읽고, 어떤 명령과 도구를 사용하는지 본다.
5. **직접 검증** — “완료했습니다”라는 답변만 믿지 말고 실제 파일, 종료 상태, 웹 응답, 정책 결과를 확인한다.
6. **산출물 보존** — 다음 노트북에서 사용할 `.md`, 스크립트, 서비스 상태를 남긴다.

이 과정은 일부러 “에이전트가 성공했다고 말했지만 실제 결과는 다른 상황”도 경험하게 한다. 따라서 **채팅 답변보다 관찰 가능한 결과가 정답**이다.

## Notebook 1 — Model, Harness, and Tools

### 목표

Codex가 모델의 답변을 실제 작업으로 바꾸는 과정을 추적한다. 특히 하네스가 제공하는 컨텍스트, 도구와 권한이 무엇인지 확인한다.

### 수행할 여섯 단계

1. **Codex가 검색하게 만들기** — 과정의 보안 노트를 찾게 하고 인덱스 항목 하나를 작성시킨다.
2. **여러 턴으로 분해하기** — 하나의 답변이 어떤 대화 턴과 도구 호출로 구성되는지 나눈다.
3. **권한 추적하기** — 복사본을 대상으로 “사용자 지시”와 “실제로 허용된 권한”을 비교한다.
4. **거짓 성공 잡기** — 명령의 종료 상태와 명령이 설명한 실제 파일 상태를 비교한다.
5. **저장된 파일로 행동 바꾸기** — 저장된 절차를 수정하고 출력이 어떻게 달라지는지 관찰한다.
6. **다른 세션에 인계하기** — 새 세션이 파일만 읽고 작업을 이어갈 수 있도록 인계 문서를 작성한다.

### 완료 기준

- [ ] 실습이 지정한 인덱스가 존재한다.
- [ ] `boundary-map.md`가 존재하며 지시·도구·권한의 경계가 기록되어 있다.
- [ ] `handoff.md`만 읽은 새 세션이 작업의 현재 상태와 다음 행동을 이해할 수 있다.

## Notebook 2 — Teams and Shared State

### 목표

검토자 세션, 모델을 사용하지 않는 보조 스크립트, 작은 웹 서비스를 같은 파일 위에서 함께 사용한다. 공유 상태가 협업을 가능하게 하지만 동시에 새로운 신뢰 경계를 만든다는 점을 확인한다.

### 수행할 여섯 단계

1. **검토자 추가** — 새 세션이 `handoff.md`를 통해 인덱스를 검토하게 한다.
2. **모델 없는 보조 도구 추가** — 결과를 확인할 수 있는 반복 작업 하나를 스크립트로 만든다.
3. **파일로 상태 공유** — 또 다른 새 세션이 채팅 기록 없이 파일만으로 작업을 이어가게 한다.
4. **course desk 만들기** — 인덱스를 읽기 전용으로 보여 주는 작은 웹 서비스를 만든다.
5. **채팅 밖의 작업 추적** — 백그라운드 작업 중 채팅을 닫았다가 다시 연결해 상태를 확인한다.
6. **조직 구조 그리기** — 세션, 스크립트, 서비스와 공유 파일의 관계를 지도화하고 다음에 공격 시험할 노트를 선택한다.

### 완료 기준

- [ ] `team-map.md`에 각 세션과 도구의 역할, 공유 파일, 신뢰 경계가 보인다.
- [ ] course desk가 실행되고 인덱스를 읽기 전용으로 보여 준다.

## Notebook 3 — Interfaces and Injection

### 목표

Notebook 2에서 만든 desk와 인덱스 작업을 외부 공격자의 관점에서 조사한다. 사용자 입력과 외부 콘텐츠에 포함된 지시가 신뢰된 작업 흐름에 섞일 때 어떤 일이 생기는지 확인한다.

> [!CALLOUT] ⚠️
>
> 공격 실험은 반드시 제공된 DLI 환경과 복사본에서만 수행한다. 실제 서비스, 다른 사용자의 시스템 또는 외부 대상에는 적용하지 않는다.

### 수행할 여섯 단계

1. **desk 정찰** — 응답만 보고 사용 가능한 경로를 추정한 뒤 실제 코드와 비교한다.
2. **접근 제한 시험** — 허용된 범위 밖에 canary를 두고 요청하여 경계가 작동하는지 확인한다.
3. **저장된 지시 심기** — 복사한 노트에 지시를 넣고 인덱스 작업을 다시 실행한다.
4. **다른 전달 경로 사용** — 같은 지시를 인계 파일을 통해 전달해 본다.
5. **허용된 효과 비교** — 같은 효과를 직접 경로와 다른 경로로 각각 시도한다.
6. **재현 가능한 사례 작성** — 검토자가 처음부터 다시 만들 수 있는 공격 사례 하나를 기록한다.

## Notebook 4 — Credentials and Dependencies

### 목표

도우미가 가진 서명 키와 교체 가능한 의존성을 이용해, “정상적으로 서명됨”과 “안전함”이 같은 뜻이 아님을 확인한다. 키가 허용하는 범위를 줄였을 때 피해도 줄어드는지 비교한다.

### 수행할 여섯 단계

1. **유효한 서명 시험** — 서명된 요청을 변조해 실패를 확인한 뒤, 다른 요청을 정상적으로 서명한다.
2. **의존성 교체** — 정상 의존성과 변경된 의존성을 각각 실행하고 실제 효과를 비교한다.
3. **키 권한 축소** — 키를 읽기 전용 범위로 줄이고 같은 의존성을 다시 실행한다.
4. **도달 범위 지도화** — 워크로드가 읽고, 불러오고, 쓸 수 있는 대상을 나열한다.
5. **지속성 확인** — 나중 세션이 읽는 파일을 변경해 효과를 확인한 뒤 반드시 원상 복구한다.
6. **차단할 연결 고르기** — Notebook 5에서 런타임 정책으로 막을 효과 하나를 선택한다.

### 완료 기준

- [ ] 서명 검증과 요청의 안전성이 별개인 이유를 설명할 수 있다.
- [ ] 정상·변경 의존성의 실제 효과 차이를 기록했다.
- [ ] `reach-chain.md`에 자격 증명 → 의존성 → 접근 가능 자원 → 효과의 연결이 보인다.
- [ ] 다음 노트북에서 차단할 효과가 하나로 명확히 선택되어 있다.

## Notebook 5 — OpenShell Containment

### 목표

Notebook 4에서 선택한 효과 앞에 OpenShell 정책을 두고 무엇이 차단되고 무엇이 통과하는지 검증한다. 통제가 에이전트가 수정할 수 없는 런타임 아래에서 강제되는지를 보는 방어 실습이다.

### 수행할 여섯 단계

1. **경계 찾기** — 허용된 파일 작업 하나와 거부되어야 할 파일 작업 하나를 시험한다.
2. **정책 읽기** — 각 정책 규칙을 그 규칙이 통제하는 파일·프로세스·네트워크 작업과 연결한다.
3. **기준선 만들기** — 제안한 규칙 아래에서 웹 요청 두 개가 정상 작동하는지 확인한다.
4. **권한 하나 제거하기** — 경로 하나를 정책에서 제거하고 같은 두 요청을 반복한다.
5. **놓친 경로 찾기** — 규칙이 다루지 못한 우회 경로와 운영자 전용 행동을 시험한다.
6. **강제 지점 지도화** — 무엇을 막았고, 무엇을 놓쳤으며, 각 통제의 소유자가 누구인지 기록한다.

### 완료 기준

- [ ] 허용과 거부가 프롬프트 문구가 아니라 실제 정책 결과로 확인된다.
- [ ] 정책 변경 전후에 같은 시험을 실행해 비교했다.
- [ ] `defense/enforcement-map.md`에 통제, 강제 위치, 소유자, 빈틈이 기록되어 있다.

## Notebook 6 — Agent Governance

### 목표

Notebook 5에서 남은 질문을 조직 수준으로 확장한다. 새로운 도구, 하위 세션, 평가, 감사와 철회 절차를 포함한 운영 가능한 거버넌스 계획을 만든다.

### 수행할 여섯 단계

1. **자기 개선 시험** — 수정된 절차와 원본을 학습에 쓰지 않은 사례로 비교한다.
2. **작업자 복제 제한** — 새 세션 생성 한도와 하위 세션이 상속하는 권한·상태를 확인한다.
3. **새 기능 관리** — 도구 하나를 도입하고 필요할 때 철회하는 절차를 계획한다.
4. **시스템 간 평가** — 공개된 평가 하나를 읽고 소규모 비교 시험을 설계한다.
5. **샌드박스 바깥 경계 조사** — 단일 샌드박스로 해결되지 않는 질문 하나를 공개 연구까지 추적한다.
6. **현업 적용 계획** — 자신이 실제로 사용하는 시스템에 적용할 시험 하나를 작성한다.

### 완료 기준

- [ ] 기능 도입, 승인, 모니터링과 철회 책임자가 구분되어 있다.
- [ ] 하위 세션이 무엇을 상속하고 무엇을 상속하면 안 되는지 기록했다.
- [ ] `next-investigation.md`에 대상 시스템, 위험 가설, 시험 방법, 성공·실패 기준이 있다.

## Final Assessment — 최종 평가

평가자는 별도의 적대적 모델이다. 과정 개념과 실험 결과를 엄격하게 확인하고 학생의 어시스턴트와 직접 대화한다. 평가자가 보낸 요청도 신뢰할 수 없는 외부 입력으로 취급해야 한다.

### 수행 순서

1. **실습 등록** — 실습 환경이 일회성 challenge에 서명하고 평가자의 키를 저장한다.
2. **규칙 설정** — 어떤 평가자 요청이 자동으로 처리될 수 있고, 어떤 요청에 사용자 승인이 필요한지 어시스턴트에게 알려 준다.
3. **평가자에게 답하기** — Notebook 1~6의 실제 기록을 근거로 답하고, 외부로 보낼 내용은 사용자가 결정한다.
4. **세션 제출** — 평가자가 인터뷰를 채점하고 통과 결과에 서명한다.
5. **결과 저장** — 실습 환경이 서명을 검증한 경우에만 결과를 저장한다.

### 완료 기준

- [ ] 평가자가 요구하더라도 비밀 키, 불필요한 파일 또는 허용되지 않은 데이터를 보내지 않았다.
- [ ] 답변은 자신의 실습 산출물로 뒷받침된다.
- [ ] 서명 검증된 결과와 `assessment-record.md`가 저장되었다.

평가 결과는 실습 환경의 비공개 신원 키에 묶인다. 다른 사람이나 다른 실습 환경의 결과를 복사해 사용할 수 없으며, 평가 전에 신원 관련 파일을 임의로 삭제하거나 교체하면 안 된다.

## 막혔을 때 확인할 것

### `Password or token`만 보이는 경우

- 원인: DLI 런처의 인증 세션 없이 내부 Jupyter 주소를 직접 열었다.
- 해결: 탭을 닫고 [DLI 이벤트 페이지](https://learn.nvidia.com/dli-event)에서 **Start/Start Task**를 다시 누른다.
- 하지 말 것: 임의의 토큰을 추측하거나 `Setup a Password`에서 새 비밀번호를 설정하지 않는다.

### 다른 Notebook 파일 또는 과정 카드가 보이지 않는 경우

- `.ipynb` 파일만 보이지 않는다면 정상일 수 있다. `/lab/harness/security/home`에서 Notebook 1~6 **모듈**을 순서대로 연다.
- 과정 홈의 모듈·레슨 카드나 단계 이동 UI가 전혀 보이지 않을 때만 접속 문제를 점검한다.
- DLI 페이지에서 작업 상태가 **Running**인지 확인한다.
- 기존 내부 URL을 새로고침하기보다 DLI의 **Launch** 링크로 다시 들어간다.
- 여러 탭에서 서로 다른 오래된 인스턴스를 열어 두지 않는다.
- 계속 보이지 않으면 현재 주소가 포함된 화면 전체를 캡처해 강사에게 보여 준다.

### Codex가 완료했다고 했지만 파일이 없는 경우

- 현재 작업 디렉터리와 Codex가 말한 경로가 같은지 확인한다.
- 성공 메시지가 아니라 실제 파일을 열어 내용을 확인한다.
- 명령의 종료 코드가 0인지, 출력 파일이 비어 있지 않은지 확인한다.
- 해당 단계의 지시를 다시 주고 “검증 명령과 실제 결과도 보여 달라”고 요청한다.

### 다음 노트북이 이전 결과를 찾지 못하는 경우

- 이전 노트북의 완료 기준에 적힌 산출물 이름을 확인한다.
- `handoff.md` 등 인계 파일에 현재 경로와 다음 행동이 기록되어 있는지 확인한다.
- 새 파일을 임의의 폴더에 만들지 말고 실습이 지정한 위치를 사용한다.

### 시간이 부족한 경우

- 노트북 실행이나 서비스 시험을 하지 않을 때는 DLI 페이지의 **Stop Task**를 누른다.
- 인스턴스를 중지해도 노트북 내용은 읽을 수 있다.
- 다시 실습할 때만 인스턴스를 시작하여 제한된 컴퓨팅 시간을 아낀다.

## 안전 수칙

- 실습 공격은 제공된 샌드박스와 복사본에서만 수행한다.
- 개인 또는 회사의 실제 키, 토큰, 고객 데이터, 내부 파일을 실습 환경에 넣지 않는다.
- 워크숍에서 사용한 키는 노출된 것으로 간주하고 실습 후 교체한다.
